# Product Requirements Document - iMaotai

**Author:** Cc
**Date:** 2026-02-18

## Executive Summary

iMaotai 是一款专为开发者设计的、基于**离线 OCR 视觉识别**与**静态 JSON 配置驱动**的安卓自动化抢购引擎。该项目不仅针对《i茅台》App，更致力于构建一个通用的、高扩展性的抢购框架。通过将抢购流程抽象为包含**置信度阈值**与**容错重试机制**的静态 JSON 描述文件，并利用针对移动端优化的本地离线 OCR 技术（配合**图像预处理策略**），用户可以实现极高鲁棒性的跨平台抢购。核心安全机制由一套分级的“防检测工具箱”组成，从基础坐标偏移到模拟**真实手指压力与采样频率**的轨迹追踪，再到环境伪装，全方位规避反自动化检测。系统专为闲置安卓设备设计，支持通过 Webhook 实现抢购结果的远程回传。

### What Makes This Special

- **极致优化的本地视觉驱动：** 采用经过轻量化处理的本地 OCR 模型（如 PaddleOCR-Mobile），并集成图像二值化预处理流程，确保在老旧闲置设备上依然具备毫秒级的识别响应速度。
- **高鲁棒性的静态任务模型：** JSON 任务模型不仅定义 UI 匹配，还支持自定义“匹配置信度”与“异常重试步长”，有效应对因 App 背景图更新或光线变化导致的识别波动。
- **生理级行为模拟系统：** 防检测 Level 2 升级为模拟真实手指的压感 (Pressure)、触摸面积 (Size) 及非均匀采样频率，使自动化操作在底层系统调用层面与真人无异。
- **四级递进式防检测开关：** 提供从 L1（基础随机化）到 L4（系统级环境伪装）的精细化控制，允许开发者根据目标 App 的风控强度灵活配置防御策略。
- **自动化的“离手”监控：** 专为长期挂机设计，集成 Server 酱、钉钉机器人等 Webhook 接口，实现抢购成功通知、设备低电量报警或异常状态的远程同步。

## Project Classification

**Technical Type:** Developer Tool / Offline Vision-Driven Automation (Enhanced Robustness)
**Domain:** E-commerce Automation / Mobile Security / Computer Vision
**Complexity:** High (Due to real-time image processing and low-level touch emulation)
**Project Context:** Greenfield - New Project

本项目的主要挑战在于：1. 在性能有限的硬件上平衡 OCR 识别精度与响应耗时；2. 持续对抗 App 不断升级的触摸行为采样分析算法。

## Success Criteria

### User Success

- **预约达成：** 程序能够稳定识别《i茅台》抢购界面，并在规定时间内自动完成预约/抢购流程。
- **及时触达：** 抢购结果（成功/失败）或关键系统异常能通过配置的 Webhook 准时推送到用户手机。
- **账号安全：** 在长期使用过程中，不因自动化脚本行为触发 App 的风控封禁或“预约黑名单”。

### Project Success (Stability)

- **长期运行稳定性：** 在闲置安卓设备上，程序能够实现 7x24 小时低功耗挂机，且非因 App 强制更新导致的流程中断率极低。
- **环境自适应能力：** 能够应对闲置设备可能出现的低电量、网络波动等基础干扰。

### Technical Success

- **防检测策略生效：** 四级防御体系（特别是模拟按压压力与随机轨迹）能有效欺骗 App 的基础行为分析模型。
- **OCR 识别鲁棒性：** 离线 OCR 在目标设备上的识别准确率足以支撑“预约”按钮的精准定位，无需人工干预校准。

### Measurable Outcomes

- **抢购成功率：** 除去官方配额限制因素，程序操作的成功执行率需达到 95% 以上。
- **维护成本：** 面对 App 界面微调，用户通过修改 JSON 配置文件恢复功能的时间不超过 10 分钟。
- **封号率为零：** 核心指标，即在使用防检测策略的情况下，封号风险降至最低。

## Product Scope

### MVP - Minimum Viable Product (最小可行性产品)

- **核心抢购引擎：** 支持《i茅台》App 的基础预约流程。
- **基础防御体系：** 实现 L1（坐标随机）与 L2（轨迹/压感模拟）防检测功能。
- **离线 OCR 模块：** 集成本地 OCR 识别引擎，支持基于文本的坐标定位。
- **静态 JSON 驱动：** 支持通过 JSON 文件配置抢购步骤。
- **Webhook 通知：** 支持至少一种主流推送渠道（如钉钉或 Server 酱）。
- **Debug Overlay：** 提供基础的悬浮窗状态展示。

### Growth Features (后期扩展)

- **多平台适配：** 扩展 JSON 任务模型，支持京东、淘宝等其他平台的抢购脚本。
- **高级防御体系：** 实现 L3（行为混淆）与 L4（环境伪装）。
- **性能优化：** 针对极低配置闲置手机的 OCR 推理加速与内存优化。

### Vision (未来愿景)

- **通用抢购协议：** 建立一套标准化的、基于视觉识别的自动化抢购描述语言，让个人开发者可以轻松共享和复用抢购逻辑。

## User Journeys

**Journey 1: Cc - “设定即忘”的晨间预约（核心路径）**
周一早晨 8:50，Cc 还在享用早餐。他那台放在书房充电的闲置安卓手机已经根据预设的定时任务自动唤醒。iMaotai 引擎启动，加载了针对《i茅台》的静态 JSON 配置文件。

8:59:55，程序开始执行。它通过本地离线 OCR 引擎，在 300ms 内精准识别出了屏幕上的“预约抢购”按钮。此时，L2 级防检测策略自动生效：点击动作并非固定坐标，而是带有一个微小的正态分布偏移，且模拟了真实手指按压 150ms 的物理特性。预约成功后，iMaotai 立即通过 Webhook 向 Cc 的手机推送了一条：“[iMaotai] 茅台预约成功！预约号：123456”。Cc 看到通知，放心地继续工作，全程无需手动触碰那台闲置设备。

**Journey 2: Cc - 5 分钟适配 UI 变更（开发者路径）**
某次 App 更新后，Cc 发现自动化流程在“选择门店”页面卡住了。他没有打开 IDE 编写代码，而是直接开启了 iMaotai 的 **Debug Overlay** 模式。在手机屏幕上，他清晰地看到 OCR 识别框覆盖在 UI 元素上，但由于门店列表的背景颜色变浅，导致识别置信度从 0.95 降到了 0.6，低于 JSON 中设定的 0.8 阈值。

Cc 拿起手机，打开 JSON 配置文件，将该步骤的 `min_confidence` 调整为 0.55，并利用图像预处理开关开启了“高对比度模式”。再次点击测试，Debug 悬浮窗立刻亮起绿灯，显示匹配成功。从发现问题到修复适配，全程只用了不到 5 分钟，充分体现了静态配置与视觉驱动的高扩展性。

**Journey 3: “沉默的守护者” - 异常处理与自恢复（运维路径）**
深夜，闲置手机因为插座松动电量掉到了 10%，同时系统弹出了一个“低电量提醒”对话框，遮挡了抢购 App 的界面。此时 iMaotai 正在进行例行的环境检查。OCR 引擎发现当前屏幕文本与 JSON 预期的“首页”文本完全不匹配。

触发“容错重试机制”后，程序在 3 次尝试失败后判定为非预期阻塞。它没有死循环，而是先通过 Webhook 向 Cc 发送了一条紧急告警：“[iMaotai告警] 屏幕匹配连续失败，当前电量 10%，请检查设备状态。”收到消息后，Cc 及时处理了硬件问题。这种异常感知的闭环确保了自动化工具 stere o 挂机时的可靠性。

## Developer Tool / CLI-Scripting Specific Requirements

### Project-Type Overview (Python + ADB Automation)

iMaotai 被定义为一个基于 Python 的自动化脚本工具，通过 Android Debug Bridge (ADB) 协议对目标设备进行远程控制。它采用“宿主机-目标机”架构（或在安卓本地 Termux 环境下运行），通过模拟 Shell 命令与输入流实现对《i茅台》App 的精准操控。

### Technical Architecture Considerations

- **核心引擎 (Python Engine)：** 采用 Python 3.x 编写，利用 `pure-python-adb` 或直接调用 `subprocess` 模块与 ADB 守护进程通信。
- **视觉处理流 (Vision Pipeline)：** 
  - **捕获：** 通过 ADB 截图命令（如 `screencap`）实时获取屏幕图像。
  - **预处理：** 利用 OpenCV 进行灰度化、二值化处理，提升 OCR 在低对比度背景下的识别率。
  - **识别：** 调用 PaddleOCR-Mobile 的 Python 推理库进行本地文字定位与提取。
- **连接模型：** 支持 USB 连接及无线 ADB (TCP/IP) 连接模式，以便于闲置手机在固定位置挂机，无需物理连线。

### Configuration & Data Schema (Local JSON)

- **任务描述文件 (Task JSON)：** 采用声明式静态 JSON。
  - 定义关键步骤的 OCR 匹配文案、最大等待时间、重试次数。
  - 支持 `target_text_offset` 字段，用于处理“点击按钮上方/下方”等特殊布局。
- **全局配置文件 (Global Config)：** 
  - 存储设备 Serial Number、Webhook 地址、离线模型路径。
  - **防检测等级开关：** `stealth_level: 1-4`，对应不同的延迟算法与轨迹参数。

### Implementation Considerations

- **坐标缩放与归一化：** 鉴于闲置手机的分辨率各异，系统需根据屏幕宽高比对 OCR 返回的坐标进行自动归一化处理，确保 JSON 任务文件的跨设备通用性。
- **ADB 稳定性管理：** 针对“挂机”场景，需实现 ADB 连接心跳检测与自动重连逻辑，避免因连接超时导致的抢购中断。
- **执行效率优化：** 优化截图传输链路，尽可能减少从手机端到 Python 环境的数据传输耗时，确保在抢购高峰时刻的响应速度。

### Output & Logging

- **标准输出 (STDOUT)：** 采用彩色控制台输出（如 `colorama`），清晰展示当前执行步数、OCR 识别详情及随机延迟数值。
- **结构化日志：** 支持同步输出为 `.log` 文件，记录每一轮预约的执行轨迹与异常堆栈。

## Project Scoping & Phased Development

### MVP Strategy & Philosophy

**MVP Approach:** 体验型 MVP (Experience MVP) —— 优先交付一个在《i茅台》平台上能够稳健运行、不被封号且具备远程通知能力的闭环工具。
**Resource Requirements:** 个人开发者环境（Python 3.x, ADB, 轻量化离线 OCR 模型）。

### MVP Feature Set (Phase 1)

**Core User Journeys Supported:**
- **Journey 1:** 自动化预约全流程（唤醒、识别、点击、通知）。
- **Journey 3:** 基础异常感知与远程告警。

**Must-Have Capabilities:**
- **Python-ADB 控制引擎：** 实现基础的设备交互与流程调度。
- **本地 OCR 定位模块：** 集成 PaddleOCR-Mobile，支持基于文本的 UI 元素查找。
- **静态 JSON 任务执行器：** 能够解析并执行针对 i茅台的预约步骤描述文件。
- **L1/L2 级防检测：** 实现坐标随机偏移、模拟真实手指压感及非均匀滑动轨迹。
- **Webhook 通道：** 至少集成一种（如 Server 酱）用于结果回传。

### Post-MVP Features

**Phase 2 (Growth):**
- **多平台通用适配：** 引入更多平台的 JSON 任务模板（如京东、淘宝）。
- **L3 行为混淆：** 在正式操作前增加模拟真人随机浏览的干扰行为。
- **调试视图增强：** 完善 Debug Overlay，支持实时参数调整。

**Phase 3 (Expansion):**
- **L4 环境伪装：** 实现系统级的特征混淆（如无障碍服务伪装）。
- **性能优化：** 针对极低配置闲置手机的推理提速。

### Risk Mitigation Strategy

**Technical Risks:** 离线 OCR 在老旧设备上的耗时较长。**应对：** 引入图像预处理（二值化）以降低计算量。
**Market Risks:** 目标 App 风控机制突变。**应对：** 保持 L1-L4 防御等级的灵活性，通过 JSON 配置快速调整策略。
**Resource Risks:** 屏幕适配问题。**应对：** 采用归一化坐标系设计，确保一份 JSON 配置适配多种分辨率。

## Functional Requirements

### 1. 自动化任务引擎 (Automation Engine)
- **FR1:** 系统可以基于预设的定时任务自动启动抢购流程。
- **FR2:** 系统可以通过 ADB 指令模拟点击、长按、滑动等基础交互动作。
- **FR3:** 系统可以根据归一化算法自动适配不同屏幕分辨率的点击坐标。
- **FR4:** 系统可以识别并处理抢购流程中的标准 UI 状态切换。
- **FR5:** 系统可以在抢购结束后自动释放资源并进入待机或关闭状态。

### 2. 视觉识别能力 (Vision Capabilities)
- **FR6:** 系统可以利用本地离线 OCR 引擎识别屏幕上的文本内容。
- **FR7:** 系统可以对原始截图进行预处理（如灰度、二值化）以提升识别精度。
- **FR8:** 系统可以根据用户设定的“匹配置信度”阈值过滤识别结果。
- **FR9:** 系统可以支持基于文本相对于特定元素的偏移坐标进行操作。

### 3. 防检测防御体系 (Stealth & Anti-Detection)
- **FR10:** 系统可以在每次点击时引入正态分布的随机坐标偏移。
- **FR11:** 系统可以模拟真实手指的物理压感 (Pressure) 变化。
- **FR12:** 系统可以模拟非均匀采样的随机滑动轨迹（贝塞尔曲线）。
- **FR13:** 系统可以在操作间隙引入符合真人特征的随机时间延迟。
- **FR14:** 系统可以根据配置等级开启或关闭特定层级的防检测手段。

### 4. 任务调度与配置 (Task Scheduling & Config)
- **FR15:** 开发者可以编写并加载静态 JSON 格式的任务描述文件。
- **FR16:** 系统可以解析 JSON 文件中的步骤、文本匹配项及重试逻辑。
- **FR17:** 系统可以读取本地全局配置文件，获取 Webhook 地址及设备信息。
- **FR18:** 系统支持通过命令行参数或配置文件定义启动时间。

### 5. 异常处理与状态监控 (Error Handling & Monitoring)
- **FR19:** 系统可以检测并记录抢购流程中的超时与匹配失败异常。
- **FR20:** 系统可以在连续匹配失败时触发预设的重试步长或中止保护。
- **FR21:** 系统可以通过 Webhook 渠道（如 Server 酱）回传执行结果日志。
- **FR22:** 系统可以在检测到低电量或设备异常时发送远程预警。
- **FR23:** 开发者可以开启悬浮式 Debug Overlay，实时观察 OCR 识别框与执行状态。

## Non-Functional Requirements

### Performance (性能要求)

- **OCR 识别时效性：** 在目标闲置设备上，单次离线 OCR 识别（从截图到返回文本坐标）的端到端耗时需控制在 800ms 以内，以确保抢购瞬时的响应速度。
- **指令执行延迟：** Python 逻辑层下达 ADB 指令至目标设备开始物理执行，其网络或协议延迟应低于 100ms（基于本地 USB 或稳定局域网）。
- **低功耗运行：** 程序在后台挂机监听时，CPU 占用率应低于 15%，以避免老旧手机因过热导致的降频或进程被杀。

### Security & Privacy (安全性与隐私)

- **全离线视觉处理：** 系统严禁将任何屏幕截图或 OCR 识别出的敏感文本（如订单号、账号信息）上传至第三方云端接口，确保开发者数据的绝对私密。
- **生理级随机化精度：** L2 级防御下的坐标随机算法，在连续 100 次模拟操作中，其像素级点击坐标的重复率需为 0%。
- **ADB 连接加固：** 支持通过加密的无线 ADB (TCP/IP) 协议连接，防止在局域网环境下被恶意劫持控制权。

### Reliability & Stability (可靠性与稳定性)

- **无人值守自恢复：** 系统需具备进程守护或周期性环境检查能力。若检测到抢购 App 异常退出或屏幕被非预期弹窗遮挡，需在 60s 内通过 Webhook 发送告警。
- **网络容错机制：** Webhook 通知接口需具备至少 3 次指数退避 (Exponential Backoff) 的自动重试逻辑，确保在网络抖动时通知不丢失。
- **环境自适应：** 系统需能识别并忽略常见的系统级弹窗（如低电量、系统更新提示），确保核心抢购流程的连续性。

### Maintainability (易维护性)

- **逻辑与配置完全解耦：** 所有的 UI 定位文案、置信度阈值、步骤逻辑必须封装在外部静态 JSON 中。开发者无需修改 Python 核心源码，即可在 5 分钟内通过更新 JSON 完成对 App 界面变更的适配。
- **结构化日志溯源：** 系统需生成包含完整时间戳、OCR 匹配详情及执行步长的结构化日志文件，便于开发者在抢购失败后进行回溯分析。
